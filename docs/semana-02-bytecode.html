Para explorar

  1. Asignaciones y operaciones. En a + b * 2, ¿qué operación se hace primero? Mira la pila justo antes y después de cada BINARY_OP.
  2. El compilador ya hizo la cuenta. El código dice 60 * 60. ¿Dónde quedó esa multiplicación en el bytecode? ¿Por qué horas * segundos sí aparece?
  3. Un if con else. ¿Cuántas instrucciones se ejecutan y cuáles nunca? ¿Qué cambiaría si la temperatura fuera 25?
  4. Un for corto. ¿Cuántas veces se ejecuta FOR_ITER? ¿Y END_FOR?
  5. Un while. La comparación n > 0 aparece dos veces en el bytecode. ¿Por qué crees que Python la puso dos veces?
  6. Una llamada a función. ¿En qué paso se crea la función doble y en qué pasos se ejecuta su código? ¿Qué pasa con la pila del módulo mientras tanto?
  7. ¿Por qué después de cada CALL a print viene un POP_TOP?

El intérprete

Cuando escribes python hola.py, el programa python (el intérprete, python.exe en Windows) hace dos cosas, siempre en este orden: primero compila todo tu archivo a bytecode y después lo ejecuta con su máquina virtual. Las dos partes viven dentro del mismo programa: por eso se siente como si Python leyera tu código directamente.

Compilar a bytecode

El compilador lee el archivo completo, revisa que respete las reglas del lenguaje (la sintaxis) y lo traduce a bytecode: una lista de instrucciones muy sencillas como LOAD_CONST o BINARY_OP. Si encuentra un error de sintaxis, se detiene aquí: por eso un SyntaxError en la última línea impide que se ejecute incluso la primera.

El compilador también hace algunas cuentas por adelantado: si escribes 60 * 60, el bytecode ya trae el 3600.

La máquina virtual

Es un ciclo que repite: toma la siguiente instrucción, la ejecuta y avanza. Trabaja con una pila de valores: las instrucciones ponen valores arriba (LOAD) o los sacan para usarlos (STORE, BINARY_OP, CALL...). Los if y los ciclos se vuelven saltos: instrucciones que cambian cuál es la siguiente. Cada llamada a una función escrita en Python crea un marco nuevo, con su propia pila y sus variables locales.

Se llama "virtual" porque no es una máquina de verdad: es un programa (escrito en C, en el caso de CPython) que se comporta como un procesador muy sencillo. El mismo bytecode corre en Windows, macOS o Linux.

__pycache__ y los archivos .pyc

Cuando un programa hace import de un módulo tuyo, Python guarda el bytecode de ese módulo en la carpeta __pycache__ para no volver a compilarlo la próxima vez (si el .py no cambió). El nombre del archivo dice qué versión lo creó:

programacion\ ├── herramientas.py ├── principal.py (hace: import herramientas) └── __pycache__\ └── herramientas.cpython-312.pyc

El archivo que corres directamente (python principal.py) se compila cada vez y no deja .pyc. Puedes borrar __pycache__ sin miedo: Python la vuelve a crear. Y no la subas a tus entregas ni a GitHub: no es código tuyo, es una copia compilada.

Ver el bytecode

En la terminal, python -m dis archivo.py muestra el bytecode de un archivo. Desde Python, import dis y dis.dis(funcion). Es una herramienta para curiosear y entender: para programar no necesitas leer bytecode.

El mismo programa, tres versiones de Python

Esto imprime python -m dis operaciones.py con a = 7, b = 5, c = a + b * 2 y print(c). En rosa, lo que cambia respecto a 3.12.

El bytecode no es parte del lenguaje: es un detalle interno de CPython y cambia en cada versión. En 3.11 la llamada usa PRECALL y CALL y el final es LOAD_CONST + RETURN_VALUE; 3.12 junta eso en RETURN_CONST; 3.14 carga los enteros pequeños con LOAD_SMALL_INT, pone PUSH_NULL después de la función y ya no muestra los números de instrucción si no se piden (-O). Tu archivo .py funciona igual en las tres; un .pyc de 3.12 no sirve para 3.14, y por eso su nombre lleva cpython-312.
